Design judgment for a "provider quota / rate-limit" capability (consult 2026-06-04, shape-only, not built).

**Step = request is the right RPD unit, but it's a lower bound with 3 named leaks.** `COUNT(conversation_step) GROUP BY provider_id, day` is the correct unit for provider RPD (one AI SDK step = one provider HTTP call; `maxRetries: 0` everywhere so no hidden retry multiplier). `getModelUsage` in `src/lib/server/db/ai/admin-queries.ts` (~:185) ALREADY does `COUNT(*) AS steps GROUP BY model` — extend with `provider_id, date_trunc('day')`, no new happy-path capture needed. Leaks that make it an undercount: (1) errored steps hit `onError`, not `onStepFinish`, so 429'd requests — the most quota-relevant — persist NO row; (2) embedding calls inside llmwiki/useRetrieval branches (`searchLlmwiki`/`retrieve`/`verifyCitations`) hit a provider but produce zero step rows — open Q whether they share the Gemini key; (3) `tryFallback` uses `createOnFinish` only (no `saveConversationStep`), so every fallback request is invisible exactly during rate-limit events. `provider_id` is nullable → pre-capture/fallback rows bucket to 'unknown' and drop out of per-provider sums.

**Don't wire response-header scraping.** AI SDK surfaces `result.response.headers` (reliable for `generateText`, unreliable for streaming — `x-ratelimit-*` dropped on streams, which is our hot path). Gemini (the provider that hits the daily wall) sends nothing on 200s; Groq has RPD+TPM not RPM; OpenAI per-minute only. Header signal is absent exactly where pre-emption matters. Instead, increment a Redis counter `ai:quota:429:{providerId}:{day}` at the two existing `rate_limit` classification sites (`classifyStreamError` ~:425 + outer catch ~:1138 in chat-orchestrator) — exact "times this provider told US no today," highest signal, zero header dependency.

**Circuit-breaker reconciliation = 3 tiers, NOT a blanket switch.** Keep reactive `markCooldown`-on-429 as the floor for all providers (only thing that handles shared-key burn by others). Pre-empt ONLY free-tier Gemini: when own-count crosses ~80% of a CONFIGURED (never guessed) RPD, `markCooldown('google', <until reset>)` — duration is "until quota reset," not 60s (a 60s cooldown is useless vs a DAILY wall; it just re-trips every 61s all day). CAVEAT: lower-bound count can only under-throttle, never over — set threshold conservative. GOTCHA: `msUntilUtcMidnight()` in budget.ts is UTC; Gemini free-tier resets midnight PACIFIC — needs a PT variant or it cools the wrong duration. Groq/OpenAI = display-only (RPM/TPM, per-minute; day-bucket is wrong granularity; reactive 60s already matches). Pre-emption shifts tool turns off free Gemini onto paid gpt-4o-mini earlier in the day → COST-BUDGET-AFFECTING → escalate to user before building.

**Display = two independent axes, never conflated.** Axis A = per-user token budget (`ai:budget:{userId}:{day}` vs `AI_DAILY_TOKEN_CAP` in budget.ts) — exact, ours, per-user, real gauge. Axis B = provider request quota — global, lower-bound, shared-key, MUST be labeled "our count / lower bound / shared key." For Gemini lead with the TRUTHFUL signals (429-count + `getCooldownResumeAt` cooldown state) and treat the RPD bar as an estimate trending toward a known wall. Never draw a unified "quota 73%" bar mixing the two axes or implying a confident denominator from a shared-key lower bound.

**How to apply:** when this feature gets built, the cheap high-signal additions are (a) extend getModelUsage with provider_id+day, (b) the 429 Redis counter, (c) close the `tryFallback` step-persistence gap. The Gemini pre-emption is the only behavior change and needs cost sign-off + the PT-reset fix. Builds on [[ai-telemetry-gap]] (the capture-vs-query asymmetry this all sits on) and [[chat-grounding-branches]] (per-branch step fidelity differs).
